# 交付纪律

> 针对 AI / Agent 协作中两类高发事故：**擅自附赠**（需求外加戏）与**复盘式交付**（把纠错过程写进标题、注释与 diff）。
> 实现边界与根因治理见 [structure.md](structure.md)；注释写什么见 [style.md](style.md) / [showcase.md](showcase.md)。冲突时以本文「禁止附赠」「禁止复盘」为准。

## 核心结论

1. 只做被明确要求的事：不附赠功能、重构、测试、文档、格式化或「顺手优化」。
2. 交付物描述**最终结果**，不描述**被撤回的方案**；禁止出现「无 X 版 / 已去掉 X / 为何不加 X」。
3. 交付前用 `git status` + `git diff` 做范围自检；越界就裁剪重提，而不是写说明解释为何越界。

## 1. 禁止附赠

### 1.1 定义

附赠 = 在未获明确授权的情况下，交付物中出现了与任务目标无关的改动或叙事。

| 类型 | 反例 | 正例 |
|------|------|------|
| 功能加戏 | 做番茄炒蛋时加东坡肉 | 只做番茄炒蛋 |
| 换皮加戏 | 纠偏去掉东坡肉后，在后续步骤中换个马甲引入东坡肘子/肉末 | 一旦被拒，同类与衍生概念彻底出圈 |
| 顺手重构 | 改一个空判时顺带重命名、抽接口、换写法 | 只改该空判 |
| 顺手格式化 | 全文件 `spotlessApply` 污染 diff | 只格式化本次触碰的行/文件 |
| 顺手补测试/文档 | 任务未要求却新增测试类或改无关 README 段落 | 仅当任务或「文档同步」表要求时才做 |
| 防御性加戏 | 为纯理论输入加校验、异常类型、兼容层 | 遵守 [structure.md](structure.md)「改动范围」 |

### 1.2 执行要求

- **默认零附赠**：任务说明未点名的文件、模块、重构、依赖变更，一律不改。
- **碰边先问**：实现过程中发现必须触及范围外文件才能完成目标时，停下说明原因并请求确认，不得擅自扩大 diff。
- **提交须授权**：未获明确要求时不得执行 `git commit` / `git push`；默认只改工作区与暂存区，由需求方决定何时落历史。
- **例外白名单**（可不另询，但仍须在交付说明中点名）：安全漏洞、数据损坏、资源泄漏、会阻断常规功能正确性的缺陷；以及 [structure.md](structure.md)「文档同步」表强制要求的文档更新。
- **格式化纪律**：优先对本次修改文件执行 `spotlessApply`，禁止无差别全仓格式化后混入同一提交。

### 1.3 规约演进与代码对齐分离（切片隔离）

- **规约升级与代码落地解耦**：当制定、重构或升级顶层规范文档（`AGENTS.md`、`docs/01-rules/*`）时，其提交必须与全仓业务/示例代码的大规模重构与风格收敛物理切开。
- **禁止混入巨石提交**：大规模代码收敛须按领域或模块拆分为独立子切片（如 `style(http): ...`、`style(bluetooth): ...`），禁止将“规约制定”与“全仓多模块普调”混入同一超大提交，确保 blame 历史可溯、单模块可独立 Review 与回滚。

## 2. 禁止复盘式交付

纠错或回滚后，交付物不得携带「曾经加过什么、为何撤掉」的过程叙事。

### 2.1 禁止出现的形态

| 落点 | 反例 | 正例 |
|------|------|------|
| 提交 / PR 标题 | `番茄炒蛋（无东坡肉）`、`移除多余的 X` | `feat(sample): 番茄炒蛋`、`fix(module_x): 修正 Y` |
| 提交正文 | 大段论述「先前方案为何不可取」 | 只写本次最终形态的「为什么」 |
| 代码注释 | `// 这里不加东坡肉，因为……`、`// 已移除旧逻辑……` | 解释**当前代码**的约束或非显而易见原因（见 [style.md](style.md)） |
| 文档 / 说明 | 「本次去掉了 A，保留了 B」 | 直接描述 B |
| Diff 内容 | 先加 B 再删 B 的对冲改动，或保留空壳/注释占位 | 干净结果：最终代码即全部 |

### 2.2 为什么禁止

- 负向标题（`（无 X）`）会在历史里永久暗示「X 是合理默认」，误导后续检索与 Review。
- 注释论述「不做什么」会随代码演进迅速过时，且违反 [style.md](style.md)「Why > What」。
- 对冲 diff 放大 Review 成本，掩盖真正变更。

### 2.3 执行要求

- 标题与提交信息只命名**最终状态**；被拒方案不进 Conventional Commits（格式见 [git.md](git.md)）。
- 注释只解释「当前为什么这样写」；禁止记录「曾经不这样写 / 为何删掉旧写法」。确需长期约束时，写**正向不变量**，不写编年史。
- 若纠错发生在**同一未推送分支**上：`git add` / `commit --amend` / 交互式整理，使历史中不出现「先附赠再删除」。**Agent 交付纠错禁止用 `--no-verify` / `COMMIT_MSG_DISABLE=1` 掩盖门禁失败**；人工明确决策下的临时跳过机制见 [git.md](git.md)。
- 会话内可以简述纠错过程；**代码、提交、PR、文档**不得复读该过程。

## 3. 范围自检清单（交付前必过）

1. `git status`：未跟踪/已修改文件是否全部在任务目标内？
2. `git diff --stat`：变更行数与文件数是否与任务复杂度匹配？有无超大无关重排？
3. 标题 / 提交信息：是否只描述结果？有无 `（无X）`、`revert` 过程、道歉或方案对比？
4. 注释增删：新增注释是否解释当前约束？有无「为何不加 / 已移除」句式？
5. 文档：是否按 [structure.md](structure.md)「文档同步」更新，且未夹带无关章节重写？
6. 任一项不过：裁剪后重验，**禁止**用额外说明把越界合理化。

## 4. 纠错后的正确交付形态

| 阶段 | 错误做法 | 正确做法 |
|------|----------|----------|
| 用户指出附赠 | 「你说得对，我去掉并写个说明」 | 「已去掉 X；标题/注释/diff 不出现 X」 |
| 改代码 | 删掉 X，但留下空方法、注释占位、兼容开关 | 彻底移除，最终树中无 X 的痕迹 |
| 提交 | `refactor: remove 东坡肉 and document why` | 在未推送历史中整理为干净的 `feat: 番茄炒蛋` |
| Review 材料 | PR 描述一节「不包含的范围」 | 只列本次交付内容；范围限制在任务单/Issue 里写，不进代码史 |

## 5. 需求侧与 Agent 侧话术

### 5.1 下达任务时（人 → Agent）

有效指令包含**目标 + 文件/模块边界 + 明确排除项**：

```text
只改 modules/module_x 下与 Y 相关的类。
不要：重构、改名、全仓格式化、补测试、改无关文档。
若必须碰到范围外文件，先停下说明。
```

纠错时锁死交付形态：

```text
删掉 X。标题、diff、注释中都不得出现 X，也不得写任何「为何不加 X」的说明。
```

### 5.2 接受任务时（Agent）

- 默认假设：**最小必要改动**；任务单未写 ≠ 需要做。
- 开工前在内部将目标收敛为「本次允许触碰的文件集合」；执行中触碰集合外路径即中断并汇报。
- 多步任务优先拆分为可独立验收的切片，每片过一遍第 3 节清单。
- 需要扩大范围时，只申请，不预支。

## 6. 一句话门禁

**做番茄炒蛋，就只交付番茄炒蛋：diff 干净，标题干净，注释干净。**
