# EventBus、RxBus、LiveEventBus、FlowEventBus 对比研究

## 结论摘要

在现代 Android 项目中，优先级通常可以这样排序：

```text
SharedFlow / FlowEventBus > 明确作用域的 ViewModel 通信 > EventBus > LiveEventBus > RxBus
```

但这不是绝对排名。真正的选型应结合项目现状：

- 新 Kotlin / 协程项目：优先使用 `SharedFlow`、`StateFlow` 或基于它们封装的 FlowEventBus。
- 老 Java / 混合 Android 项目：greenrobot EventBus 仍然稳定可用。
- 已深度使用 RxJava 的项目：RxBus 可以作为过渡方案，但不建议为了消息总线新引入 RxJava。
- 旧 MVVM + LiveData 项目：LiveEventBus 可减少手动生命周期管理，但新功能更建议迁移到 Flow。
- 核心业务状态不建议依赖全局消息总线，应优先使用明确作用域的数据流、Repository、ViewModel 或导航结果回传。

## 一句话定位

| 方案 | 本质 | 最适合 | 最大短板 |
|---|---|---|---|
| EventBus | 注解式发布/订阅库 | Java/老 Android、简单全局事件 | 不原生感知生命周期，事件流向隐式 |
| RxBus | 用 RxJava `Subject` 自行封装的总线模式 | 已全项目 RxJava 化 | 没有标准实现，生命周期、背压、线程安全都要自己兜底 |
| LiveEventBus | 基于 `LiveData` 的消息总线 | 旧 MVVM + LiveData 项目 | `LiveData` 更偏状态而非事件，`postValue` 可能合并事件 |
| FlowEventBus | 基于 `SharedFlow` / 协程的消息总线 | Kotlin、协程、Compose、现代 Jetpack 项目 | 需要正确设计 scope、buffer、replay 和生命周期收集 |

## 核心机制

### EventBus

EventBus 通常指 greenrobot EventBus。它通过 `@Subscribe` 注解声明订阅方法，按事件类型分发消息。

主要特性：

- 支持多种线程模式：`POSTING`、`MAIN`、`MAIN_ORDERED`、`BACKGROUND`、`ASYNC`。
- 支持 Sticky Event，即保留某类事件最近一次值，新订阅者注册后可收到。
- Java 友好，接入成本低。
- 性能和成熟度较好，适合遗留 Android 项目。

主要问题：

- 不原生感知 Android 生命周期，需要手动 `register` / `unregister`。
- 事件发布者和订阅者之间是隐式关联，长期使用会让调用链难以追踪。
- 容易把业务状态变成全局广播，导致模块边界变模糊。

### RxBus

RxBus 不是单一官方库，而是一种常见封装方式。典型实现基于 RxJava 的 `PublishSubject`、`BehaviorSubject` 或 `SerializedSubject`。

常见结构：

```kotlin
object RxBus {
    private val bus = PublishSubject.create<Any>().toSerialized()

    fun post(event: Any) {
        bus.onNext(event)
    }

    fun <T> observe(clazz: Class<T>): Observable<T> {
        return bus.ofType(clazz)
    }
}
```

主要特性：

- 可直接使用 RxJava 操作符，如 `filter`、`map`、`debounce`、`throttleFirst`、`observeOn`。
- 与 RxJava 技术栈融合度高。
- 可测试性较好，能使用 `TestObserver` 等工具。

主要问题：

- `PublishSubject` 不缓存历史事件，也不支持背压。
- 多线程调用 `onNext` 需要序列化，通常要使用 `toSerialized()`。
- 如果把 `onError` 或 `onComplete` 暴露出去，总线可能被终止。
- 生命周期需要手动管理 `Disposable`。
- 没有统一标准实现，每个项目封装质量差异很大。

### LiveEventBus

LiveEventBus 是基于 `LiveData` 的事件总线方案，常见卖点是生命周期感知、Sticky、AndroidX 支持和低侵入接入。

主要特性：

- 借助 `LiveData.observe(owner)` 获得生命周期感知能力。
- 观察者通常只在 `STARTED` / `RESUMED` 状态下接收数据。
- 可减少 EventBus 手动反注册带来的泄漏风险。
- 对老 MVVM + LiveData 项目接入成本低。

主要问题：

- `LiveData` 的语义更偏“状态持有”，不是严格事件队列。
- 新观察者可能收到旧值，容易造成重复导航、重复 Toast、重复弹窗。
- 多次 `postValue` 在主线程尚未执行时可能只派发最后一个值。
- 线程和缓冲能力不如 RxJava / Flow 灵活。
- 新项目中技术趋势已逐渐转向 Flow / SharedFlow。

### FlowEventBus

FlowEventBus 一般指基于 Kotlin `SharedFlow`、`MutableSharedFlow` 或 `StateFlow` 封装的事件总线，也可以指第三方 FlowEventBus 库。

典型实现：

```kotlin
object FlowBus {
    private val events = MutableSharedFlow<Any>(
        replay = 0,
        extraBufferCapacity = 64
    )

    suspend fun post(event: Any) {
        events.emit(event)
    }

    fun tryPost(event: Any): Boolean {
        return events.tryEmit(event)
    }

    inline fun <reified T> observe(): Flow<T> {
        return events.filterIsInstance<T>()
    }
}
```

主要特性：

- `SharedFlow` 是热流，适合向多个 collector 广播事件。
- `replay` 可实现 Sticky 语义。
- `extraBufferCapacity` 和 `onBufferOverflow` 可显式控制缓冲和溢出策略。
- 与协程、ViewModel、Compose、Lifecycle 生态天然契合。
- 可配合 `repeatOnLifecycle` 做生命周期安全收集。

主要问题：

- 需要正确设计 coroutine scope，否则可能泄漏或提前取消。
- `replay = 1` 会导致新订阅者收到旧事件，可能造成重复消费。
- `replay = 0` 则订阅前发送的事件不会被新订阅者收到。
- buffer 太小可能挂起或丢事件，太大可能积压。
- 如果封装过度，依然会变成隐式全局依赖。

## 关键维度对比

| 维度 | EventBus | RxBus | LiveEventBus | FlowEventBus |
|---|---|---|---|---|
| 生命周期感知 | 否，手动注册/反注册 | 否，靠 `Disposable` / RxLifecycle | 是，依赖 `LiveData` | 可做到，依赖 `repeatOnLifecycle` 或库封装 |
| 线程切换 | 强，内置 ThreadMode | 很强，Rx Scheduler | 较弱，主要围绕主线程观察 | 强，Coroutine Dispatcher / Flow 上下文 |
| Sticky 支持 | 内置 `postSticky` | 取决于 Subject 类型 | 支持 | `replay > 0` 可实现 |
| 背压/缓冲 | 不适合高频流 | `Observable` / `Subject` 无背压，需额外设计 | `LiveData` 存在合并语义 | 可配置 buffer 和 overflow 策略 |
| 有序性 | 同线程/部分模式较明确 | 单线程序列化下可控，多线程需小心 | 主线程派发，连续 `postValue` 可能合并 | 单个 Flow 内有序，跨 dispatcher/scope 需设计 |
| 错误处理 | 订阅方法异常需关注 | `onError` 可能终止 bus | 无 Rx 式终止 | Flow 异常随 coroutine 传播，可局部 `catch` |
| 类型安全 | 按 Class 类型，较隐式 | `ofType`，中等 | key/string + type，易写错 key | 可用 `reified` 做类型安全封装 |
| 可测试性 | 一般，隐式全局状态 | 好，Rx 测试工具成熟 | 一般，LiveData 测试需规则 | 好，可配合 coroutine test / Turbine |
| 维护趋势 | 老牌稳定 | Android 新项目中降温 | 偏旧 LiveData 生态 | 与 Kotlin / Jetpack 趋势一致 |

## 常见坑位

### EventBus 的坑

EventBus 容易让代码“表面解耦，实际全局耦合”。发布者不知道谁在消费，消费者也很难从局部代码看出事件来源。项目规模变大后，事件名、事件类型和注册位置会成为隐性维护成本。

建议：

- 不要用 EventBus 承载核心业务状态。
- 事件类命名应清晰，例如 `UserLoggedOutEvent`，不要使用 `MessageEvent` 这类泛化名称。
- 注册和反注册应放在清晰、成对的生命周期位置。
- 避免跨太多模块广播同一类事件。

### RxBus 的坑

RxBus 最大风险来自 `Subject` 的错误封装。`PublishSubject` 不保留历史事件、不支持背压；多线程发送时必须保证序列化；如果外部能访问 `Subject`，误调用 `onError` 或 `onComplete` 会让整个总线失效。

建议：

- `Subject` 必须私有化。
- 对外只暴露 `Observable`，不要暴露 `Subject`。
- 使用 `toSerialized()` 处理多线程发送。
- 不要通过总线传输高频、大量、不可丢的数据。
- 生命周期中及时 dispose。

### LiveEventBus 的坑

LiveEventBus 的核心矛盾是：`LiveData` 更像状态容器，而消息总线处理的是一次性事件。页面旋转、重新观察、进程恢复等场景可能导致旧事件再次派发。另一方面，连续 `postValue` 可能被合并，只剩最后一次值。

建议：

- 不要用它承载严格事件队列。
- 谨慎使用 Sticky。
- 导航、弹窗、Toast 等一次性事件要额外做消费保护。
- 新功能优先考虑 `SharedFlow`。

### FlowEventBus 的坑

FlowEventBus 的优势是显式可控，风险也来自这些配置本身。`replay`、buffer、overflow、scope、collector 生命周期都要明确。如果默认参数没想清楚，照样会出现重复消费、事件丢失或协程泄漏。

建议：

- UI 层使用 `repeatOnLifecycle` 收集事件。
- 一次性事件通常使用 `replay = 0`。
- 需要 Sticky 时才设置 `replay > 0`。
- 对可能突发的事件设置合理 `extraBufferCapacity`。
- 不要把全局 `ApplicationScope` 滥用于所有事件。

## 选型建议

### 新 Kotlin / 协程项目

优先选择 Flow 生态。多数情况下，不需要引入一个名为 EventBus 的库，可以直接使用：

- `SharedFlow`：适合一次性事件、广播事件。
- `StateFlow`：适合状态。
- `Channel`：适合点对点事件，但要注意生命周期和消费方数量。
- `ViewModel` 共享：适合同一 Activity / Navigation Graph 下的页面通信。

如果确实需要跨模块广播，再封装一个小型 FlowEventBus。

### 老 Java / 混合项目

EventBus 依然是现实可用的选择。它稳定、接入简单、Java 友好。如果项目已经大量使用 EventBus，除非正在做系统性架构迁移，否则不建议为了“现代化”强行替换。

更合理的策略是：

- 限制新增 EventBus 使用范围。
- 清理泛化事件类型。
- 为关键事件补测试或日志。
- 新 Kotlin 模块逐步迁移到 Flow。

### 已有 RxJava 项目

如果项目仍深度依赖 RxJava，RxBus 可以继续使用，但应把封装收紧。不要让业务代码直接操作 `Subject`，也不要让错误信号终止全局总线。

如果项目已经开始迁移协程，不建议继续扩大 RxBus 使用面。

### 旧 LiveData 项目

LiveEventBus 适合低成本补生命周期感知，但它不是现代 Android 新项目的首选。对于一次性 UI 事件，尤其是导航、弹窗、Toast，需要特别小心重复消费和事件合并问题。

### 跨进程 / 跨 App 通信

不要默认选消息总线。跨进程或跨 App 场景应优先考虑：

- Binder / AIDL
- BroadcastReceiver
- ContentProvider
- DataStore / 文件 / 数据库同步
- 系统服务或明确的 IPC SDK

消息总线库的跨进程能力通常是库层封装，不应替代正式 IPC 架构设计。

## 推荐实践

### 一次性 UI 事件

推荐：

```kotlin
private val _events = MutableSharedFlow<UiEvent>(
    replay = 0,
    extraBufferCapacity = 1
)
val events = _events.asSharedFlow()
```

UI 收集：

```kotlin
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.events.collect { event ->
            handleEvent(event)
        }
    }
}
```

### 页面状态

推荐使用 `StateFlow`，而不是 EventBus：

```kotlin
private val _uiState = MutableStateFlow(UiState())
val uiState = _uiState.asStateFlow()
```

### 全局事件

如果必须使用全局事件，应满足：

- 事件类型明确。
- 事件数量可控。
- 不承载核心状态。
- 不作为模块间主要调用方式。
- 有清晰的生命周期和测试策略。

## 最终建议

如果是新项目，我会优先使用 `SharedFlow` / `StateFlow`，只在确实需要跨模块广播时做一个轻量 FlowEventBus。

如果是遗留项目，不要为了替换而替换：

- 已有大量 EventBus：先规范事件类型和注册边界。
- 已有 RxBus：先收紧 Subject 封装，避免错误终止和生命周期泄漏。
- 已有 LiveEventBus：新代码逐步迁移到 Flow，旧代码按风险分批处理。

消息总线应该是补充手段，不应成为主要架构。越关键的业务状态，越应该使用显式的数据流和明确的作用域。
